# Digital Studio Pro

An operator-led local publishing workflow: edit a title, brand, ordered sections,
lesson content, practice activities, quiz questions and optional answer notes;
generate a real fillable PDF; review those exact bytes; download or explicitly
save them to managed Files. No AI text, AI images, revenue or account data is invented.

## Parent integration

Load `static/css/u1-studio-pro.css` and `static/js/u1-studio-pro.js` after
`u1-data.js`, `u1-core-workspaces.js` and preferably `u1-life-studio.js`.
The script registers `U1CoreViews.register('studio', renderer)`. The original
life-studio renderer is retained as `U1Life.renderStudio(host)`, with a return
button to this editor. All six original printable templates and all five legacy
workbook templates retain their existing routes and layouts. Pro offers editable
section structures for those same eleven categories; its calendar and colouring
structures are workbooks, not replacements for the original calendar grids or art.

After the parent's safety gate, dispatch both GET and POST to:

```python
from utils.u1_studio_pro import handle_request
if handle_request(self):
    return
```

Only `/api/workspace/studio-pro` is matched (query strings are ignored). The
handler returns `True` for every response on that path and `False` for other
paths. Origin protection uses `handler.integration_request_allowed()` for both
methods. POST additionally requires the current `integrations_hub.CSRF_TOKEN`
in `X-U1-CSRF`, `Content-Type: application/json`, and a bounded Content-Length.
The existing `U1Data.post` supplies local authorisation automatically.

## Route contract

GET returns `success`, eleven `templates` (`id`, `title`, suggested empty
`sections`), `capabilities`, `limits`, `providers`, and `notice`.
Capabilities reflect actual imports in the server runtime. Both provider states
are `not_connected`. No installation or external request is performed.

Creation POSTs accept exactly `action` and `document`. `action` defaults to `render`:

```json
{
  "action": "render",
  "document": {
    "title": "Your product title",
    "subtitle": "Your optional subtitle",
    "audience": "Your intended readers",
    "template": "course",
    "version": "1.0",
    "source": "Your content provenance",
    "brand": {"name": "Your brand", "accent": "#176B64", "font": "serif"},
    "fillable": true,
    "include_answer_notes": false,
    "sections": [{
      "title": "Your section title",
      "content": "Your original lesson content",
      "activity": "Your practice activity",
      "answer_notes": "Your optional operator notes",
      "quizzes": [{"question": "Your question", "answer_notes": "Your explanation"}]
    }],
    "instructions": "Your reader instructions",
    "licence": "Your licence text"
  }
}
```

- `render`: returns base64 PDF `content`, `filename`, `mime`, `size`, `sha256`,
  `metadata`, `pages`, `section_pages` (zero-based section `index`, `title`,
  one-based PDF `page`), `fields`, `fillable`, `hyperlinks`, and `artifacts`.
  Also returns `preview_signature` and `preview`, a first-page PNG artifact when
  pypdfium2 is installed, or null when the page-image renderer is unavailable.
- `artwork`: validates the same document and returns `metadata` plus `artifacts`.
  It works without reportlab. Also returns the validated, default-completed
  `document` used by project import. Each `cover`/`mockup` artifact has base64 `content`,
  `filename`, SVG `mime`, `size` and `sha256`.
- `bundle`: requires nonempty user instructions and licence. Returns the render
  metadata and statistics, with the main artifact changed to a ZIP and a `members`
  list. Members are the PDF, cover SVG, mockup SVG, `INSTRUCTIONS.txt`,
  `LICENCE.txt`, `metadata.json`, and `README.txt`. Answer notes are omitted from
  both learner PDF and ZIP unless explicitly included. The ZIP has no project
  JSON or other hidden source containing excluded notes.
- `preview`: accepts exactly `{action:"preview",content,signature,page}` instead
  of `document`. `content` is the base64 PDF returned by `render`, `signature` is
  its `preview_signature`, and `page` is a one-based integer. Returns `success`
  and a PNG artifact (`content`, `mime`, `filename`, `size`, `sha256`, `page`).
  The HMAC verifies that the PDF was generated by this server process before
  passing it to PDFium. Arbitrary uploaded PDFs cannot be rendered. Restarting
  the server invalidates signatures; generate the PDF again afterward.

Status codes: `200` success; `400` malformed, unsupported or oversized fields;
`403` origin/CSRF rejection; `405` unsupported method; `415` wrong content type;
`503` missing PDF dependency. Error responses are `{success:false,error:...}`.
Responses are JSON with `Cache-Control: no-store` via the shared response helper.

## Bounds and output safety

The creation request limit is 262,144 bytes. Signed preview requests support up
to 12 MB of JSON and PDFs up to 8 MB; generated PDFs share that 8 MB bound.
A document supports 1-24 sections and up to 8
questions per section, with a maximum of 240 PDF pages. The combined normalized
JSON content limit is 100,000 characters. Individual maximums are: title 120,
subtitle 280, audience 240, version 24, source 300, brand name 80, section title
160, lesson content 6,000, activity 2,000, section answer notes 3,000, quiz
question 600, quiz answer notes 1,500, instructions and licence 12,000 each.
Title, version, brand name and section titles must be single lines. Typography
is `serif` or `sans`; accent must be `#RRGGBB`; boolean fields require booleans.
Unknown keys, duplicate JSON keys, deep malformed JSON, invalid types, control
characters and unsupported text glyphs are rejected. PDF text currently supports
Western Latin characters through built-in PDF fonts. Text is escaped in SVG and
rendered as plain text in PDFs; user HTML, scripts, links or paths are not executed.

Output names use a fixed `u1-` prefix and ASCII slugs of title/version, with no
directory separators or dot segments. ZIP members are constructed by the server,
never accepted as paths. There are no user-selected file reads, network calls or
persistent writes in this module. Processing uses bounded in-memory buffers.

## Editing, preview and save semantics

Drafts and reusable brand preferences are browser-local. Project JSON export and
validated import preserve the full editable draft, including operator notes.
Section order is controlled by accessible Up/Down buttons; sections can be
duplicated, removed and restored with one-level undo. Applying a new empty
structure or importing a project asks before replacing the current draft.

Generate preview is explicit. The main preview displays page images rendered
directly from the returned PDF bytes, with page selection and Previous/Next.
An optional interactive iframe displays the returned PDF Blob; its download and
managed Files save use those same base64 bytes. Editing invalidates
export/save buttons until a fresh preview is generated. If edits occur during a
generation request, its stale response is rejected. Contents entries, PDF
bookmarks and footer links navigate sections. Selecting an editor section opens
that section's first PDF page. The external viewer link is a local Blob URL.
The editor never frames `/classic` or `/studio.html`. If the parent has registered
`U1CoreViews.supports('images')`, the Connections area adds an optional
`data-go="images"` button labelled `AI image provider setup`; otherwise it is
absent. This link does not imply an image provider is connected.

ZIP generation rebuilds the same current document, so PDF timestamps/byte hashes
inside a ZIP can differ from a previous preview. Its content and settings match
the reviewed revision. The cover SVG is a separate marketing cover, not a pixel
copy of the workbook's PDF title page. The mockup uses the same cover SVG geometry.

Saving to Files is only triggered by the explicit button. `U1StudioPro.saveFile`
uses these existing APIs, without real account calls:

```text
POST /api/workspace/prism/upload-start
{name, mime, size, folder: "Digital Studio"}

POST /api/workspace/prism/upload-chunk
{id, offset, content: "base64 of at most 32768 binary bytes"}
```

Every acknowledged offset is checked, and the final chunk must report
`status: "ready"`. A failed save reports its upload ID and explains how to remove
an unfinished upload from Files before retrying. It never reports an unconfirmed
save as complete. Title/version/source are embedded in PDF metadata (custom
`/U1*` keys when pypdf is installed) and ZIP `metadata.json`; the existing Files
API stores ordinary file name/MIME/folder fields, not a new metadata database.

## Dependencies and limitations

The checked project `.runtime` has reportlab, pypdf and pypdfium2 installed. Reportlab creates
measured, paginated content, links, bookmarks, and multiline AcroForm response
fields. Pypdf preserves the form tree and adds custom metadata. Without pypdf,
reportlab still produces interactive PDFs and standard title/subject metadata.
PDFium renders the exact PDF into PNG page previews under a process lock because
PDFium is not thread-safe. Without it, the interactive viewer and reader download
remain available, with an explicit page-image preview limitation.
Without reportlab, artwork and original basic printables remain available; PDF
and ZIP creation return an honest dependency error. No dependency is installed
by the handler or editor.

PDF viewers vary in form support. Fill and save a downloaded copy in a compatible
reader; browser form edits are not captured back into the Studio source or its
export bytes. Each response field accepts up to 3,000 characters. There is no
automatic marking, AI lesson writing, AI image generation, Canva sync, checkout,
licence authoring or revenue estimation. Use Connections to authorise a supported
provider when integrated; use Prompt Builder for briefs, or manually import the
PDF/SVG into your own Canva account today. No text is sent to these services by
this editor.

## Reviewed Studio-to-product handoff

After a current generated PDF or ZIP is confirmed ready in managed Files, the
editor enables **Review catalogue handoff**. The review displays the real ready
file ID, filename, checksum and artifact version. The operator reviews title,
audience and description and explicitly approves the handoff. Optional checklist
items are individually unchecked until selected. Draft edits invalidate the
handoff review and require a current preview/save again; regenerating an identical
document may reuse the already saved artifact during the same editor session.

Two additional POST actions use the existing Studio route and its origin/CSRF
guards. Parent routes and assets need no additional wiring:

```text
{action:"handoff-review", file_id, receipt}
{action:"handoff", file_id, receipt, reviewed:true,
 product:{title,audience,description}, expected_product_version:0, checklist:[]}
```

`receipt` is the `handoff_receipt` returned by PDF/ZIP generation. Its signed
artifact metadata binds the filename, MIME, size, checksum, title, version and
canonical document fingerprint. The backend verifies it against an undeleted,
fully received `ready` Files row. Receipts are process-bound; after a server
restart, regenerate/save to obtain a current receipt. Arbitrary file paths or
unsigned metadata cannot be used. The review response includes `file`, `artifact`,
proposed `product`, `existing`, `expected_product_version`, and `publishes:false`.
Pass its expected version into confirmation.

Confirmation delegates to the same `u1_personal_core.action` operation used by
`POST /api/workspace/personal`, with `action:create` and `kind:product`. A new
record has status `review`, the actual artifact `current_version`, and a version
entry referencing the ready file. No publication, scheduling, pricing claim or
account action is performed. No new record store is introduced.

Duplicate checks include active and archived products. A stable document marker
or the same file/version reuses the matching product. PDF and ZIP exports of the
same canonical document can link to one product/version. Existing catalogue
details are preserved. Archived products, ambiguous matches and changed current
versions require operator resolution in Income. Optimistic record versions
reject conflicting updates with `409`. Exact retries reuse the prior record.
The shared application lock serializes concurrent Studio handoffs in the normal
single-process server; this is not a distributed idempotency mechanism across
independent server processes.

At most six distinct operator-approved checklist titles (160 characters each)
create ordinary `kind:launch` records linked to the product in `backlog`. Existing
matching tasks are reused, including archived tasks with an explanatory warning.
If checklist creation partially fails, the product and completed tasks are
returned with `partial:true`, `pending_checklist`, and `warnings`. Retrying adds
only missing tasks; it does not duplicate the product. The success response also
includes `product`, `reused`, `file_id`, `launches`, and `publishes:false`.
Catalogue title/audience/description limits are 160/300/4000 characters. These
actions retain the standard 256 KB creation-request bound.
